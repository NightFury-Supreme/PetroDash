# 13. GLOBAL API ERROR STANDARDIZATION

Remove hardcoded and inconsistent API error JSON responses.

All relevant endpoint failures must use the application's standard `AppError` architecture.

Establish one predictable response contract.

Conceptually:

```json
{
  "success": false,
  "error": {
    "code": "TICKET_NOT_FOUND",
    "messageKey": "errors.tickets.notFound",
    "details": {}
  }
}
```

Use the existing application's actual response contract where one already exists. Do not introduce a conflicting second error format.

Requirements:

* Standardized `AppError`
* Predictable machine-readable error codes
* Centralized error middleware
* Stable HTTP status mapping
* Stable frontend error identification
* No endpoint-specific random JSON error formats
* No stack traces to clients
* No database/provider internals exposed to users
* No sensitive information leakage
* Structured details only when safe and required
* Unknown/unhandled failures normalized by central middleware

Where applicable, align the public semantics with RFC 7807 while preserving the project's established contract.

# 41. TRANSLATION JSON — STRICT SEMANTIC MESSAGE/CODE DEDUPLICATION

Translation JSON files must be treated as a **canonical message system**.

The same semantic meaning must use **one canonical translation key/code across the application**.

Do **not** create, preserve, or introduce multiple translation keys merely because the English wording is slightly different.

For example, do not create or keep:

```json
{
  "continue": "Continue",
  "proceed": "Proceed"
}
```

when both are used for the same user action and have the same semantic meaning.

Likewise, do not create multiple keys such as:

```text
errors.failed
errors.requestFailed
api.requestFailed
common.requestFailed
```

when they represent the same underlying user-facing condition.

## Mandatory rule

**One semantic meaning = one canonical translation key/code.**

The exact wording does **not** determine whether messages are duplicates.

Determine equivalence by:

* Semantic meaning
* User intent
* Application behavior
* Error condition
* Action being performed
* Context and usage
* Whether the user would understand both messages as the same message

Two sentences with different wording but the same semantic meaning must normally share one canonical key.

## Mandatory search before creating any key

Before creating, renaming, or preserving a translation key:

1. Search **all translation JSON files and namespaces**.
2. Search for exact wording.
3. Search for synonyms and similar wording.
4. Search for semantically equivalent messages.
5. Search for equivalent error conditions.
6. Search for equivalent actions.
7. Search all code consumers of those keys.
8. Identify the existing canonical key.
9. Reuse the canonical key where the meaning is equivalent.
10. Consolidate duplicates where safe.
11. Update every consumer.
12. Update **every supported locale**.
13. Remove obsolete duplicate keys from every locale.
14. Re-scan after the migration.

Do not create a new key simply because an existing key has a different name.

## Semantic duplication examples

These may represent the same semantic message:

```text
Continue
Proceed
Go ahead
```

These may represent the same semantic failure:

```text
Request failed
Unable to complete request
The request could not be completed
```

These may represent the same user action:

```text
Delete
Remove
Delete item
Remove item
```

Do not automatically merge messages solely because the words look similar. Inspect their actual application meaning and usage first.

The rule is **semantic equivalence**, not blind string matching.

## Translation key normalization

When duplicate semantic keys already exist:

```text
Duplicate keys
    ↓
Search all consumers
    ↓
Compare actual semantics and usage
    ↓
Select canonical key
    ↓
Update every consumer
    ↓
Update every supported locale
    ↓
Remove obsolete duplicate keys
    ↓
Run another repository-wide search
    ↓
Verify no duplicate semantic identifiers remain
```

Do not leave duplicate keys simply because they exist in different modules, namespaces, or locale files.

Do not create module-specific copies of an existing globally equivalent message unless the semantics are genuinely different.

## Same meaning must use the same code everywhere

This rule applies not only to translation JSON keys, but also to related machine-readable identifiers where the same semantic condition is being represented.

Review and normalize:

* Translation keys
* Error codes
* Message identifiers
* Status identifiers
* Notification identifiers
* Validation message identifiers

Do not have different modules independently invent identifiers for the same semantic condition.

Machine-readable codes must remain stable and language-neutral.

User-facing translations must map from those canonical identifiers.

## All locale files must remain synchronized

Whenever a canonical translation key is:

* Added
* Renamed
* Consolidated
* Modified
* Split
* Moved
* Removed

apply the corresponding change to **every supported locale**.

Never update only the English/default locale.

Never leave an obsolete duplicate key in another locale.

Never leave one locale using an old key while another uses the new canonical key.

## Final semantic-duplication audit

Before completion, perform a final audit across all affected translation resources and consumers for:

* Duplicate meanings
* Duplicate action messages
* Duplicate error meanings
* Synonym-based duplicate keys
* Near-duplicate messages
* Multiple keys for the same UI concept
* Multiple error codes for the same condition
* Multiple status identifiers for the same semantic state
* Locale files with inconsistent key structures
* Obsolete keys still referenced by source code
* Keys existing in only some supported locales
* Different message keys used for the same semantic meaning in different modules

The final codebase must have **one canonical translation/message key for each genuinely identical semantic message**.

### Absolute rule

**Do not create two codes for the same meaning.**

**Do not keep two codes for the same meaning.**

**Do not justify duplicate codes merely because the wording is different.**

**Do not continue past an existing duplicate without investigating it first.**

**Search first, identify the canonical key, reuse it, migrate consumers, update every language, remove the duplicate, and verify again.**
