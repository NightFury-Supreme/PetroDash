# 4. MODULEIZATION REQUIREMENT

The target domain must be fully componentized and modular.

Every significant feature must have clear ownership.

Use a structure appropriate to the existing framework, for example:

```text
feature-domain/
├── index.ts
├── components/
├── hooks/
├── services/
├── schemas/
├── types/
├── constants/
├── utils/
├── tests/
└── translations/
```

Do **not** blindly copy this structure if the existing architecture uses a better equivalent. Preserve architectural consistency while enforcing the same separation of responsibilities.

## Module encapsulation

Every distinct module/domain must expose a controlled public API.

Preferred:

```ts
import { FeatureView, useFeature } from "@/feature-domain";
```

Avoid:

```ts
import { useFeature } from "@/feature-domain/hooks/useFeature";
```

Internal implementation details must remain internal wherever practical.

No unnecessary deep imports across module boundaries.

# 8. FRONTEND ARCHITECTURE

## API access

UI components must not directly perform API calls.

Forbidden inside presentational/UI components:

```ts
fetch(...)
axios(...)
```

Network access must go through the application's request/service abstraction and appropriate domain hook/service layer.

Recommended flow:

```text
Page
  ↓
Feature Component
  ↓
Feature Hook
  ↓
Feature Service/API Client
  ↓
Backend Endpoint
```

Components should handle presentation and user interaction.

Hooks should coordinate state and feature behavior.

Services/API modules should handle communication.

---

# 9. BACKEND ARCHITECTURE

Use clear separation:

```text
Route
  ↓
Controller
  ↓
Validation
  ↓
Service
  ↓
Repository/Data Access
  ↓
Database
```

## Routes

Routes must wire dependencies only.

Do not place database queries or business logic inside route definitions.

Bad:

```js
router.get("/", async (req, res) => {
  const users = await User.find();
  res.json(users);
});
```

## Controllers

Controllers should:

* Extract request data.
* Validate input.
* Call services.
* Map results to response contracts.
* Return responses consistently.

Controllers must not contain substantial business logic.

## Services

Services own:

* Business logic
* Database access/repository coordination
* Transactions
* Cache operations
* Third-party integrations
* Domain-level error generation
* Consistency guarantees

# 11. GLOBAL API ERROR STANDARDIZATION

Replace hardcoded and inconsistent JSON API errors.

All endpoint failures must use the application's standard error model based on `AppError`.

Implement a predictable, centralized contract.

Conceptually:

```json
{
  "success": false,
  "error": {
    "code": "FEATURE_RESOURCE_NOT_FOUND",
    "messageKey": "errors.feature.resourceNotFound",
    "details": {}
  }
}
```

The exact shape must follow the existing architecture where one exists. Do not introduce a conflicting second error contract.

Requirements:

* Standard `AppError` usage.
* Predictable machine-readable error codes.
* Centralized error middleware.
* Consistent HTTP status mapping.
* No endpoint-specific random JSON error shapes.
* No leaking stack traces or sensitive internals to clients.
* No sensitive database/provider errors exposed directly.
* Preserve structured metadata needed by clients.
* Ensure unknown/unhandled failures are converted into the standard format.
* Ensure frontend can reliably identify errors by error code/message key.

Where appropriate, align the public problem-details semantics with RFC 7807 while preserving the project's established API contract.

# 12. FRONTEND ERROR HANDLING + LOCALIZATION

The frontend must consume the standardized backend error contract.

Requirements:

* Never hardcode user-facing API errors.
* Map backend error codes to translation keys.
* Use localized messages for every supported locale.
* Provide safe fallback behavior for unknown error codes.
* Do not display raw server/internal error messages unless explicitly designed as safe user-facing content.
* Toasts, dialogs, drawers, forms, inline errors, banners, and page-level errors must all use the same localization strategy.
* Error messages must be consistent across the application.

Example concept:

```text
API error code
    ↓

Translation key
    ↓
Current locale
    ↓
User-facing message
```

## Translation key reuse

Before creating a new key:

1. Search all existing translation resources.
2. Find whether an equivalent message already exists.
3. Reuse the existing key when semantically identical.
4. Do not create duplicate translation keys for the same message.
5. Where equivalent wording exists under multiple keys, consolidate to the canonical key when safe.

### Same message ⇒ same key

The same semantic message must use the same translation key throughout the application.

Do not create:

```text
errors.failed
errors.requestFailed
common.requestFailed
api.requestFailed
```

for the same semantic message.

Use one canonical key.

### Locale completeness

Every newly introduced translation key must exist in every supported language.

Do not leave:

* Missing keys
* Empty translations
* Placeholder translations
* English fallback text disguised as translations
* Partially translated messages

Any existing untranslated text discovered within scope must be translated into all supported locales.

Use the project's existing language/locale conventions.

Do **not** add comments that look like an AI coding agent talking to itself, explaining its actions, reasoning, intentions, or implementation process.

The codebase must **never** contain comments such as:

Do not add verbose comments that simply restate obvious code, narrate implementation steps, describe what the agent just changed, or explain trivial logic.

Comments must be **professional, concise, technically meaningful, and written as permanent codebase documentation**, not as development-session notes.

Allowed comments should be limited to cases where they provide genuine long-term value, such as:

* Non-obvious business rules
* Security considerations
* Important architectural constraints
* Complex algorithms
* External protocol/API behavior
* Intentional performance decisions
* Compatibility requirements
* Necessary rationale for unusual implementation decisions

Prefer self-documenting code, clear naming, modular functions, and appropriate abstractions instead of explanatory comments.

Before completion, perform a repository-wide review of modified files and **remove any newly introduced AI-style, conversational, redundant, temporary, debugging, or unnecessary comments**.

The final code should read as if it was written and maintained by a professional software engineering team, without any obvious AI-generation artifacts.
